## 셸 / PowerShell

### PowerShell cwd 드리프트 → 상대경로 bootRun 실패 (2026-06-09)
- **증상**: `backend\gradlew.bat -p backend bootRun`이 `... does not contain a Gradle build` 또는 `backend\backend\...` 경로로 실패. 로그 파일도 엉뚱한 곳에 생성.
- **원인**: Bash 툴에서 `cd backend` 한 게 하네스 cwd에 반영돼, 이후 PowerShell 호출의 cwd가 루트가 아니라 `backend`였음. 상대경로 `backend\...`가 `backend\backend\...`로 두 번 붙음.
- **처방**: 운영 스크립트는 **절대경로로 못박는다.** `$root="c:\gitProject\SideProjectWeb"; & "$root\backend\gradlew.bat" -p "$root\backend" bootRun *>&1 | Tee-Object "$root\backend\build\x.log"`. 로그 폴링/조회도 절대경로로.

### `Set-Location`이 다음 호출에 지속 → 상대경로 Test-Path 오판 (2026-06-11)
- **증상**: FE 검사하며 `Set-Location frontend` 한 뒤, 다음 호출에서 `Test-Path backend/.env`가 **False** → "`.env` 없으니 bootRun 못 함, 런타임 검증 불가"라고 **잘못 결론**(실제로는 `backend/.env` 존재). 사용자가 "전에 검증 됐는데 왜?"로 지적.
- **원인**: PowerShell 툴은 **cwd가 호출 간 지속**된다. `Set-Location frontend` 상태라 `Test-Path backend/.env`가 `frontend/backend/.env`를 확인. + Glob은 **`.gitignore`를 준수**해서 gitignore된 `.env`·`docker-compose.yml`이 "No files found"로 나와 "파일 없음" 오판을 거들었다.
- **처방**: 존재 여부 판단은 **절대경로 Test-Path**로(상대경로 금지). 운영 호출 앞에 `Set-Location <repo root>`로 cwd를 못박고 시작. **gitignore된 파일은 Glob로 안 보임** → `.env`/compose 확인은 `Test-Path '절대경로'`로. "없다"고 단정하기 전에 절대경로로 재확인.

### native exe(mysql/docker) stderr + `$ErrorActionPreference="Stop"` → 스크립트 중단 (2026-06-09)
- **증상**: `docker exec ... mysql ... 2>&1 | Where-Object {...}`가 `mysql: [Warning] Using a password ... insecure` 경고에서 `NativeCommandError`로 터지며 그 줄에서 스크립트 전체가 멈춤(이후 HTTP 호출 등 미실행).
- **원인**: PowerShell 5.1은 native exe의 stderr 한 줄을 ErrorRecord로 감싸고, `Stop`이면 그걸 종료 오류로 본다.
- **처방**: native exe 호출엔 **`2>$null`**(에러스트림을 네이티브 단에서 버림 → PowerShell이 안 감쌈). `Stop` 스크립트 안에서 docker/mysql은 별도 호출로 빼거나 `2>$null`. `2>&1`로 합치지 말 것.

### run.ps1은 `backend/`에서 실행 가정 (2026-06-09)
- **증상**: 루트에서 `& backend\run.ps1` → `gradlew bootRun`이 루트엔 gradle 빌드 없다며 실패.
- **원인**: `run.ps1`이 `gradlew.bat bootRun`을 cwd 기준으로 호출(프로젝트 디렉터리 `-p` 미지정).
- **처방**: `-p`로 프로젝트 디렉터리를 못박아 직접 기동. `.env` 로드 + `gradlew.bat -p <backend절대경로> bootRun`. (run.ps1을 쓰려면 cwd가 backend여야 함.)

### Bash 툴도 cwd 지속 → `git commit -F .git/...` 상대경로 실패 (2026-06-16)
- **증상**: `git commit -F .git/COMMIT_EDITMSG_X`가 `could not read log file 'backend/.git/...'`로 실패(커밋 안 됨). 직전 `cd .../backend && ./gradlew test`의 cwd가 남아 있었음.
- **원인**: **Bash 툴도 호출 간 cwd가 지속**된다(PowerShell처럼). `-F .git/...`는 cwd 기준 상대경로라 `backend/.git/...`로 해석. (git 자체는 상위로 .git을 찾아 add/commit/checkout은 되지만, `-F`가 가리키는 파일 경로는 cwd 기준이라 어긋남.)
- **처방**: 운영 git은 **`git -C <repo절대경로>` + `-F <절대경로>`**로 못박는다. 또는 커밋 직전 cwd를 repo root로. 상대경로 `-F` 금지.

## Docker / MySQL

### `docker exec -i ... -e "쿼리"` → stdin 대기로 hang (2026-06-09)
- **증상**: 단발 SQL 조회인데 명령이 안 끝나고 백그라운드로 매달림(빈 출력).
- **원인**: `-i`(interactive, stdin 유지)인데 파이프로 들어올 stdin이 없어 대기. `-e`는 실행 후 종료지만 `-i`가 세션을 붙잡음.
- **처방**: 단발 쿼리는 **`-i` 빼고** `docker exec commerce-mysql mysql -ucommerce -p"$pw" commerce -e "..." 2>$null`. (`-it`는 TTY 필요한 대화형에서만.)

### bootRun이 `Communications link failure`/`Connection refused` — MySQL 컨테이너 죽어 있음 (2026-06-10)
- **증상**: bootRun이 `com.mysql.cj.exceptions.CJCommunicationsException: Communications link failure`(또는 `Unable to determine Dialect`)로 기동 실패. 직전엔 잘 됐는데.
- **원인**: MySQL 컨테이너가 그새 **Exited(255)**. 세션 사이/시간 경과로 컨테이너가 죽어 localhost:3307 연결 거부.
- **처방**: bootRun **전에 컨테이너 살아있는지 확인**: `docker inspect -f "{{.State.Health.Status}}" commerce-mysql`(또는 `docker ps`). 죽어 있으면 `docker compose -f backend\docker-compose.yml up -d` → healthy 대기 후 기동. 데이터는 named volume이라 보존됨.

### 한글 LIKE 패턴이 PowerShell→docker stdin에서 깨짐 (이월 교훈)
- **증상**: `WHERE x LIKE '%한글%'`가 매칭 0(오탐). DB 값 자체는 정상 UTF-8.
- **원인**: PowerShell→docker stdin 전송 중 코드페이지로 한글이 깨짐.
- **처방**: 한글 비교는 LIKE 말고 **HEX/CHAR_LENGTH**로 검증. 콘솔에 깨져 보여도 DB/JSON은 UTF-8 정상일 때가 많음.

## Flyway / JPA (ddl-auto: validate)

### `double` 필드 ↔ MySQL `double` 컬럼은 validate 통과 (2026-06-09, V12 확인)
- **확인**: Java `double feeRate` ↔ Flyway `fee_rate double NOT NULL` → 기동(validate) 통과. 비율 같은 비-금액은 double 컬럼 OK. **돈(원)은 여전히 `bigint`(long).**
- **처방**: 비율/소수 필드는 `double NOT NULL` DDL로 두면 됨. 금액은 절대 double 금지.

### 손수 쓴 enum 컬럼은 값 집합을 **알파벳순**으로 (이월 교훈)
- **원인**: Hibernate가 `@Enumerated(STRING)`을 MySQL 네이티브 ENUM으로 매핑 → 마이그레이션의 `enum('A','B',...)` 값 순서가 다르면 validate 실패.
- **처방**: 마이그레이션 enum 값 나열을 **알파벳순**으로(엔티티 enum 상수도 알파벳순 유지). 컬럼 추가는 기존 행 위해 `NOT NULL DEFAULT '...'` 백필.

### @Modifying(clearAutomatically=true)가 flush 안 된 보류 변경(삭제)을 버림 (2026-06-12, 리뷰)
- **증상**: 리뷰 삭제 API가 200·상품 평점 카운터는 감소했는데 **review 행이 안 지워짐**(런타임 검증서 `COUNT(*)=1`로 발각). 단위 테스트는 리포지토리를 목킹해 못 잡음 → **런타임에서만 드러남**.
- **원인**: 서비스에서 `reviewRepository.delete(review)`(영속성 컨텍스트에 삭제 예약, 아직 flush 안 됨) 직후 `@Modifying(clearAutomatically=true)` 벌크 UPDATE(`decrementRating`) 호출. clearAutomatically가 **flush 전에 컨텍스트를 비워** 예약된 DELETE가 사라짐. (IDENTITY `save()`는 즉시 flush라 INSERT/increment는 안전했지만, `delete()`는 commit까지 지연돼 당함.)
- **처방**: @Modifying 벌크 쿼리가 같은 tx의 엔티티 변경과 섞이면 **`flushAutomatically = true`도 함께** 켠다 → 벌크 op 전에 보류 변경을 flush(반영)하고 clearAutomatically로 이후 stale read를 막는다. `@Modifying(flushAutomatically = true, clearAutomatically = true)`.

## 런타임 검증 (bootRun + HTTP)

### config-driven 동작은 env var로 런타임 데모 가능 (2026-06-09, 확인됨)
- **확인**: `@Value("${payment.unavailable-providers:}")` 같은 설정값은 bootRun 시 **env var로 주입된다**(Spring relaxed binding: `payment.unavailable-providers` ← `PAYMENT_UNAVAILABLE_PROVIDERS`). MPG-stretch 페일오버를 `$env:PAYMENT_UNAVAILABLE_PROVIDERS="KAKAOPAY"` 한 줄로 시연(yml 수정·재빌드 불필요).
- **처방**: 설정 분기(페일오버/플래그)를 런타임 데모할 땐 yml 건드리지 말고 **기동 직전 `$env:<UPPER_SNAKE>="..."`** 후 bootRun. `--args="--prop=val"`보다 PowerShell 인용이 깔끔.

### 검증 후 캐노니컬 복원은 필수 (상시)
- **처방**: 검증으로 만든 데이터는 끝나고 되돌린다 — `DELETE FROM mismatch/settlement_entry/payment/order_item/orders;`, `UPDATE product_option SET stock=50 WHERE id=1;`, `UPDATE member SET role='USER' WHERE email='buyer@commerce.com';`(검증 위해 ADMIN 승격했으면). 인메모리 PG 원장은 앱 종료로 리셋. 검증 끝나면 bootRun(TaskStop) 종료.
- **계정**: buyer@commerce.com/buyerpass1234(USER). ADMIN API는 buyer를 SQL로 ADMIN 승격 후 **재로그인**(role=JWT 클레임). 같은 member라 ADMIN 세션으로 본인 주문 생성·결제·취소까지 다 됨 → 한 세션으로 끝낼 수 있음.
- **데모 시드 계정**(dev 프로파일 `DemoDataSeeder`): demo1~3@commerce.com / **demopass1234**(role USER). ADMIN 화면 검증은 `UPDATE member SET role='ADMIN' WHERE email='demo1@commerce.com';` 후 재로그인. (buyer는 시드 코드가 읽기만 하고 생성은 안 하니, 확실히 존재하는 demo1을 쓰는 게 안전.) 검증 끝나면 `role='USER'`로 복원.
- **데모 계정 전체**(2026-07-29~ 시드): demo1~3@·buyer@(USER) · seller1@·seller2@(SELLER) — 전부 **demopass1234**. **admin@commerce.com은 `app.demo-seed.admin-password`가 설정된 경우에만 생성**(로컬 dev는 yml에 있어 자동, 배포는 `APP_DEMO_SEED_ADMIN_PASSWORD` 명시 시에만 — 공개 데모 보호). ⚠️ 이미 존재하는 계정은 비밀번호를 덮지 않는다(멱등) → 옛 DB에서 demopass1234로 로그인 안 되면 그 계정은 예전 비번을 그대로 쓰는 중.
- **데모 쿠폰 코드**(2026-07-29~ 시드): `WELCOME5000`(정액 5천·3만 이상) · `SPRING10`(10%·최대 2만·5만 이상) · `MAISON15`(메종클레이 셀러 부담 15%) · `FIRSTCOME10K`(선착순 발급형·100장, demo1~3은 이미 보유). 체크아웃에서 코드 입력하거나 쿠폰함에서 선택.
- **시드가 잔재를 지운다**(2026-07-29~): dev 기동 시 `load-*` 회원·`부하테스트*` 쿠폰·`DEMO-SEED-*` 상품·빈 `AuditSmoke` 카테고리를 정리한다. **부하 테스트를 다시 돌린 뒤 재기동하면 그 결과가 사라진다** — 측정치는 기동 전에 기록할 것. 이력(주문·리뷰·감사) 있는 데이터는 보존되므로 실데이터는 안전.
- **시드가 안 돌 때**(2026-07-29~): 게이트가 `@Profile("dev")`가 아니라 **`app.demo-seed.enabled`**다. 로컬은 `application-dev.yml`이 ON으로 덮으므로 `run.ps1`(dev 프로파일)이면 자동. 프로파일 없이 `bootRun`만 하면 시드가 안 돈다 → `APP_DEMO_SEED_ENABLED=true`. 카탈로그 12종도 이 시드가 만든다(초기 P01~P07은 첫 기동에 새 이름으로 rename되고 id는 유지).
- **셀러 콘솔 계정**(2026-07-28~ 시드): seller1@commerce.com(메종클레이) · seller2@commerce.com(노드폼컴퍼니) / **demopass1234**(role SELLER·sellerId 연결됨). `/seller` 화면·셀러 알림·반품 승인 검증용. 브랜드 귀속=Maison Clay→셀러1, Daily Form·Nord Atelier→셀러2라 **후디+팬츠 주문이 멀티셀러**(shipment 2건)가 된다. ⚠️SQL로 role만 SELLER로 바꾸면 sellerId가 없어 콘솔이 403 — 승격은 반드시 `Member.assignAsSeller`(또는 시드).

## 프론트엔드 (Next.js / dev 서버)

### `next dev` 도는 중 `next build` 실행 → `.next` 손상 (2026-07-09)
- **증상**: FE 코드 검증하려 `npm run build`를 돌렸더니 EPERM(`.next\trace` open 실패), 이후 dev 서버가 `MODULE_NOT_FOUND`·`next-font-manifest.json ENOENT`·`routes-manifest.json ENOENT`·`Cannot find module './331.js'`로 깨져 모든 라우트 500. **코드는 tsc/lint 통과라 무결**이었는데 서버만 죽음.
- **원인**: `next dev`와 `next build`가 **같은 `.next` 디렉터리**를 공유. dev 서버가 쓰는 중에 build가 파일을 덮/삭제 → dev 서버의 `.next` 캐시 손상.
- **처방**: **dev 서버 기동 중엔 `next build` 금지.** FE 코드 검증은 **`npx tsc --noEmit`(+`next lint`)로 충분**(`.next` 안 건드림). 꼭 build까지 확인하려면 **dev 서버 먼저 정지**. 손상 복구 = dev 정지(포트3000 프로세스 kill) → `rm -rf .next` → `npm run dev` 재기동.

### 주석 안 `*/`(예: `h-*/w-*/rounded-*`)가 블록 주석 조기 종료 (2026-07-09)
- **증상**: `Skeleton.tsx` JSDoc과 `globals.css` 주석에 Tailwind 글롭 예시 `h-*/w-*/rounded-*`를 적었더니, TSX는 `TS1005 ';' expected`(파싱 깨짐), CSS는 cssnano **`Unexpected '/'`**로 빌드 실패. 둘 다 "왜 안 되지" 하고 두 번 겪음.
- **원인**: `h-*` 다음 `/w-*`의 **`*/`가 `/* ... */` 블록 주석을 조기 종료** → 뒤 텍스트가 코드/CSS 셀렉터로 파싱됨. TSX(JSDoc)·CSS 주석 문법 동일.
- **처방**: 주석에 **`*/` 시퀀스가 생기지 않게** 쓴다(예: "높이·너비·rounded" 또는 `h-_ w-_`처럼). Tailwind 임의값/글롭을 주석 예시로 넣을 때 `*` 바로 뒤 `/`를 피할 것.

## 테스트 / Gradle

### 전체 스위트 고부하에서 타이밍 테스트 flaky → 단독 그린 (2026-07-24)
- **증상**: `./gradlew test` 전체 실행에서 `LockComparisonTest`(DIY lease 만료·Redisson watchdog, 2s작업 vs 1s lease) 2건 FAILED. 그러나 `--tests "*LockComparisonTest"` **단독은 BUILD SUCCESSFUL**.
- **원인**: 실시간 타이밍(sleep/lease 만료 경계)에 의존하는 테스트라, 여러 gradle 빌드를 연달아 돌린 머신 고부하에서 스레드 스케줄 지연으로 경계가 흔들림. 코드 결함 아님(동시성 로직·격리 무관, 내가 만진 order/payment 경로와 별개).
- **처방**: 전체 스위트에서 타이밍 테스트가 깨지면 **단독 재실행으로 부하성 flaky인지부터 확인**(코드 회귀로 오진 금지). 진짜 회귀는 단독에서도 깨진다. #1 같은 무거운 작업 뒤 전체 스위트는 머신이 식은 뒤 한 번 더.
