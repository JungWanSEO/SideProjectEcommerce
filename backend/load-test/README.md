# 부하 테스트 (k6)

선착순/캐시 같은 동시성·성능 작업을 **실제 HTTP 부하**로 검증한다. 단위 테스트가 "로직이 맞나"라면
부하 테스트는 "부하에서도 맞고 빠른가"를 본다.

## 실행 방법 (무설치 — Docker)

앱이 8080에 떠 있어야 한다(`./run.ps1`). k6는 컨테이너로 돌리고, 컨테이너에서 호스트 앱은
`host.docker.internal`로 친다(MySQL/Redis와 같은 방식).

```bash
# backend/ 에서
docker run --rm -i -e BASE_URL=http://host.docker.internal:8080 -e VUS=20 -e DURATION=20s \
  grafana/k6 run - < load-test/cache-throughput.js
```

## ⚠️ 테스트 환경 함정 (중요 교훈)

처음 50 VU로 돌렸더니 ~8,600 RPS에서 **응답이 멈췄다**. 앱 로그엔 에러가 없었고(HikariPool 고갈·예외 없음)
중단 후에도 앱은 17ms로 정상 응답 → 범인은 앱이 아니라 **Docker Desktop(Windows)의 NAT 경로**였다.
k6 컨테이너가 `host.docker.internal`로 호스트를 초고RPS로 때리면 그 NAT 계층이 포화된다.

> **부하 테스트 제1원칙: 측정 대상(앱)이 아니라 테스트 장비/네트워크가 병목이면 숫자가 오염된다.**
> 그래서 부하를 NAT 한계 아래(20 VU)로 낮춰, 앱 자체의 차이를 쟀다. 진짜 처리량 한계를 보려면 k6를
> 네이티브로(또는 앱과 같은 도커 네트워크에서) 돌려야 한다.

## 시나리오 A: 캐시 처리량 (`cache-throughput.js`)

같은 상품 1건(`GET /api/products/1`)을 20 VU가 20초간 반복 조회. 캐시 **ON**(Caffeine) vs **OFF**(NoOp,
`APP_CACHE_ENABLED=false`)를 같은 부하로 대조. (hot key 하나만 때려 캐시 효과를 고립시킨다.)

### 결과 (2026-06-29, 로컬 · 20 VU · 20s)

| 지표 | 캐시 ON | 캐시 OFF | 차이 |
|---|---|---|---|
| 처리량(RPS) | **3,148/s** | **591/s** | **약 5.3× ↑** |
| 지연 p95 | **3.26 ms** | **43.26 ms** | **약 13× ↓** |
| 지연 평균 | 2.17 ms | 33.67 ms | 약 15× ↓ |
| 실패율 | 0.01%* | 0.00% | — |

\* ON의 실패 20건/15.6만(0.01%)·꼬리 지연은 위 NAT 잔여 잡음. OFF는 RPS가 낮아 NAT를 안 건드려 깨끗.

### 왜 이런 차이가 나나

- **지연**: OFF는 요청마다 DB 왕복이 **3번**(상품 + 카테고리·브랜드 이름 enrich) → 동시성 하에서 ~33ms.
  ON은 Caffeine 메모리에서 바로 → ~2ms(DB 왕복 0). 메모리 조회는 µs, DB 왕복+쿼리는 ms 단위.
- **처리량**: OFF는 **DB 커넥션 풀(Hikari 기본 10) + DB 처리량**이 천장 → ~591 RPS에서 막힘
  (OSIV가 요청당 커넥션을 잡고 20 동시요청이 10개를 두고 경쟁). ON은 DB 의존이 없어 CPU/네트워크만 한계.
- **ON의 3,148 RPS는 앱의 진짜 천장이 아니다** — 위 NAT 한계에 먼저 막힌 값. 즉 **캐시 이득의 하한**이다
  (실제 앱은 캐시된 읽기를 훨씬 더 처리할 수 있다).

### 한 줄 요약

> hot 읽기 경로에 캐시를 깔면 같은 부하에서 **p95가 13배 빨라지고 처리량이 5배 이상** 늘었다.
> "캐시 무효화는 어렵다"가 비용이라면, 이 수치가 그 비용을 감수할 이유다.

## 시나리오 B: 선착순 쿠폰 정합성 + 락 모드 대조 (`coupon-claim.js`)

**200명이 동시에 100장 한정 쿠폰을 받으면 정확히 100장만 발급되는가?** 를 실제 HTTP로 증명하고,
락 모드(`APP_LOCK_PROVIDER=none|redis|redisson`)별 처리량/실패를 대조한다.

- `setup()`: 어드민 로그인→100장 한정 쿠폰 생성, 회원 200명 가입+로그인해 각자 `access_token` 쿠키 수집.
  (k6는 HTTP 클라이언트라 httpOnly 쿠키도 `res.cookies`로 읽힌다.)
- `per-vu-iterations` vus=200 iter=1: VU 200명이 각자 1번씩 거의 동시에 claim(선착순 몰림 재현).
- 정합성 게이트: `claim_success count<=100` (초과 발급 0 자동 검증).

### 결과 (2026-06-29, 로컬 · 200명 동시 · 100장 한정)

| 락 모드 | 발급(201) | 마감(409) | 503 타임아웃 | claim p95 | 초과 발급 |
|---|---|---|---|---|---|
| **none** (DB 원자 UPDATE) | **100** | **100** | 0 | **1.34s** | **0** ✓ |
| **redis** (DIY SETNX 스핀락) | 52~93* | 0 | 107~148* | 3.06s | **0** ✓ |
| **redisson** (RLock pub/sub) | **100** | **100** | 0 | 2.76s | **0** ✓ |

\* DIY는 실행마다 편차(스핀락 핸드오프가 racy).

### 왜 이렇게 나오나 (핵심)

1. **정합성(초과 발급 0)은 세 모드 모두 지킴.** 이유=`claim` 안의 **DB 원자 조건부 UPDATE**가 최종 보증.
   → "분산락은 정합성 보증이 아니라 advisory"라는 설계가 부하에서도 사실로 확인됨(docs/distributed-lock-study.md).
2. **가용성/UX는 천차만별:**
   - **none**: DB 행 락이 폴링·앱 타임아웃 없이 200명을 효율적으로 직렬화 → 100 발급·100 깔끔한 sold-out·0 실패. **가장 빠름**.
   - **redis(DIY 스핀락)**: 획득을 `50ms마다 재시도(spin) + 3s 대기 한도`로 한다. 200명이 한 락에 몰리면 50ms 폴링이
     핸드오프를 throttle → 초당 ~20건만 통과 → 뒤쪽 ~절반이 3s를 못 버티고 **503**. **쿠폰이 다 팔리지도 못함**(발급<100).
   - **redisson(pub/sub)**: 락 해제 시 **즉시 깨움**(폴링 X) → 핸드오프가 빨라 200명이 3s 안에 다 통과 → none과 같은
     100/100/0. 단 Redis 왕복 오버헤드로 none보다 약간 느림(p95 2.76s vs 1.34s).
3. **단일 인스턴스에선 분산락은 순수 오버헤드** — none이 가장 빠르고 깔끔. 락의 값어치는 다중 인스턴스에서나 난다.
4. **DIY vs 라이브러리, 부하에서 극명**: 앞선 watchdog(작업 길이) 비교에 이어, 이번엔 **핸드오프 효율**(스핀 폴링 vs
   pub/sub)에서 차이. 스핀락은 고경합에서 타임아웃으로 무너지고, Redisson은 견딘다.

### 한 줄 요약

> **초과 발급 0은 세 모드 다 지켰다(DB가 보증). 하지만 단일 인스턴스에선 락이 도움이 아니라 비용이고,
> 특히 DIY 스핀락은 고경합에서 절반을 503으로 떨군다. "정합성=DB, 락=다중인스턴스 advisory"가 수치로 증명됐다.**
