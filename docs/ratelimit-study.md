# 레이트 리밋 알고리즘 비교 실습 (고정/슬라이딩/토큰 버킷)

> 분산 레이트 리밋을 포트-어댑터로 구현하며 **윈도우 알고리즘**을 대조한 학습 노트.
> 분산락 비교 실습([distributed-lock-study.md](distributed-lock-study.md))의 짝 — "DIY(우리 Lua) vs 라이브러리(Redisson)" 구도를 레이트 리밋에 적용했다.

---

## 1. 문제 — "T당 N회"에서 T를 어떻게 재느냐

레이트 리밋은 전부 *"기간 T 동안 N회까지"* 다. 알고리즘 차이는 오로지 **"T라는 시간 창을 어떻게 측정하느냐"** 하나. 로그인 5회/분을 기준으로 본다.

## 2. 알고리즘 4종

| 방식 | 경계 버스트 | 비용 | 버스트 허용 | Redis 구현 |
|------|:--:|:--:|:--:|------|
| 고정 윈도우 | ❌ 최대 2배 누수 | 최저(카운터 1) | 갑작스러움 | `INCR`+`EXPIRE` |
| 슬라이딩 윈도우 **로그** | ✅ 없음 | 높음(요청마다 저장) | 매끈 | 정렬셋(ZSET) |
| 슬라이딩 윈도우 **카운터** | ✅ 거의 없음 | 낮음(카운터 2) | 매끈 | 2×`INCR`+가중합 |
| 토큰 버킷 | ✅ 없음 | 낮음 | **의도적 허용** | Lua / Redisson `RRateLimiter` |

### 2.1 고정 윈도우 — 단순하지만 경계 버스트
시간을 `now/window` 칸으로 쪼개 칸별 카운터. 구현 최저비용(카운터 1개)이지만 **칸 경계에 요청을 몰면 두 칸에 각각 한도까지 통과**해 짧은 시간에 ~2배가 샌다(아래 §5에서 테스트로 증명).

### 2.2 슬라이딩 윈도우 로그 — 정확, 비쌈
요청마다 타임스탬프를 저장하고, 매 요청 시 *(now − T)보다 오래된 것을 버리고* 남은 개수를 센다. "지금부터 정확히 과거 T"를 매번 다시 계산하므로 경계 누수가 없다. 대가는 메모리(요청마다 원소; 키당 최대 limit개, T 후 자동 만료).

### 2.3 슬라이딩 윈도우 카운터 — 실무 절충
현재 칸 + 직전 칸 카운터 2개만 두고, 직전 칸을 겹치는 비율만큼 가중 합산(`현재 + 직전×겹침비율`). 경계 버스트를 부드럽게 누르면서 로그보다 훨씬 가볍다(Cloudflare 방식). **본 프로젝트는 학습상 더 명확한 로그 방식을 채택.**

### 2.4 토큰 버킷 — 버스트 허용, 평균 제어
버킷에 토큰을 일정 속도로 채우고(1분에 limit개) 요청마다 1개 소비. 토큰이 없으면 거부. 평소 안 쓰면 토큰이 쌓여 **순간 버스트(최대 버킷 용량)** 를 허용하되 평균은 limit/분으로 수렴. API 레이트 리밋의 사실상 표준이며 .NET `TokenBucketRateLimiter`와 동형.

## 3. 우리 구현 — 한 포트, 세 어댑터

[`RateLimiter`](../backend/src/main/java/com/commerce/api/global/ratelimit/RateLimiter.java) 인터페이스(포트) + 토글(`app.ratelimit.provider`). 분산락·캐시와 같은 포트-어댑터 패턴.

| provider | 어댑터 | 알고리즘 | 분산 |
|----------|--------|----------|:--:|
| `memory`(기본) | `InMemoryRateLimiter`(Caffeine) | 고정 윈도우 | ❌(인스턴스별) |
| `redis` | `RedisSlidingWindowRateLimiter`(DIY Lua) | 슬라이딩 윈도우 로그 | ✅ |
| `redisson` | `RedissonRateLimiter`(`RRateLimiter`) | 토큰 버킷 | ✅ |

호출부(로그인·쿠폰 claim)는 인터페이스만 의존 → 코드 변경 없이 토글로 교체. `enabled=false`면 `NoOpRateLimiter`(테스트 기본).

## 4. 슬라이딩 윈도우 로그 — ZSET + Lua

키별로 요청을 `{score=발생시각ms, member=유일값}`로 정렬셋에 쌓고, 원자 Lua로 처리:

```lua
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)  -- ① 윈도우 밖(오래된) 제거 = 왼쪽 포인터 전진
local count = redis.call('ZCARD', key)                -- ② 현재 윈도우 안 개수
if count < limit then
    redis.call('ZADD', key, now, member)              -- ③ 이번 요청 기록
    redis.call('PEXPIRE', key, window)                --    무요청이면 키 자동 소멸
    return 1
end
return 0
```

**코딩테스트의 슬라이딩 윈도우(투 포인터)와 같은 원리**: 오른쪽 포인터로 새 원소 추가(`ZADD`), 왼쪽 포인터로 범위 밖 원소 제거(`ZREMRANGEBYSCORE`), 윈도우 크기(`ZCARD`)를 항상 정확히 유지. 자료구조만 *배열 → 시간축 정렬셋*, *인메모리 → 분산*. ①②③을 **Lua로 한 번에** 묶어 "읽고-쓰기 사이 끼어듦"(경합)을 막는다(분산락 해제를 Lua로 한 것과 같은 이유).

> **설계 노트** — ①시각을 앱에서 넘기므로 다중 인스턴스 시계 편차에 살짝 의존(정밀하게는 Lua 안 `redis.call('TIME')`로 단일 시계). 레이트 리밋은 ms 정확성이 중요치 않아 앱 시각으로 충분. ②member는 같은 ms 동시 요청도 구별되게 유일값(UUID).

## 5. 경계 버스트 대조 — 테스트로 증명

[`RateLimiterComparisonTest`](../backend/src/test/java/com/commerce/api/global/ratelimit/RateLimiterComparisonTest.java) — **가짜 시계를 주입**해 경계를 결정적으로 재현(벽시계 의존 제거 → 흔들리지 않음). 한도 5/윈도우 1초:

```
한 칸 끝자락(t=999ms)에 5건 + 다음 칸 시작(t=1000ms)에 5건  (≈1ms 사이 10건)
─────────────────────────────────────────────────────────────────
고정 윈도우 : 999→칸0(5 통과) · 1000→칸1(5 통과)        = 10 통과  💥 2×한도 누수
슬라이딩   : 1000에서도 999의 5건이 최근 1초 안 → 거부   =  5 통과  ✅ 정확히 한도
```

→ `assertThat(fixedAllowed).isEqualTo(10)` · `assertThat(slidingAllowed).isEqualTo(5)` **PASS**. 슬라이딩 윈도우가 고정 윈도우의 경계 버스트를 제거함을 코드로 못박았다.

## 6. DIY(Lua) vs 라이브러리(Redisson)

분산락 실습과 같은 대조:

- **DIY 슬라이딩(Lua)**: 알고리즘을 직접 통제(슬라이딩 로그). 원자성·경합을 우리가 Lua로 보장. 메커니즘 학습에 최적.
- **Redisson 토큰 버킷(`RRateLimiter`)**: 분산 토큰 버킷을 라이브러리가 구현(원자성·만료 위임). 코드는 거의 0이나 알고리즘은 토큰 버킷으로 고정됨.

> 둘은 **구현·알고리즘이 다르나 외부 계약은 같다**(한도 초과 시 429). 슬라이딩은 "정확히 최근 N"(무차별 차단에 빡빡), 토큰 버킷은 "평균 + 버스트 허용"(일반 API에 관대).

## 7. 선택 가이드 & 한계

| 상황 | 추천 |
|------|------|
| 단일 인스턴스·간단 | `memory`(고정 윈도우) — 외부 0 |
| 무차별 로그인 차단(정확·평탄) | `redis`(슬라이딩) |
| 일반 API·버스트 관대 | `redisson`(토큰 버킷) |

**기본값**: 단일 인스턴스 데모라 `memory`(opt-in으로 분산). **한계/후속**: ①Redis 통합 테스트는 로컬 Redis 의존(`assumeTrue` skip) → Testcontainers로 무조건화. ②슬라이딩 카운터(2-카운터 근사) 미구현 — 로그 방식만. ③부하 테스트(k6)로 처리량·정확도 수치화는 후속. ④호출부 윈도우는 1분 고정(시그니처 `check(key, limitPerMinute)`).
