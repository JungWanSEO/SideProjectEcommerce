### 어드민 반품 관리
- **`GET /api/returns/admin?status=&type=&sellerId=`**: nullable 바인딩 필터(생략하면 그 조건 무시)·최신순. 운영 동선이 "REQUESTED만 모아 대행 승인"이라 상태·유형·셀러 셋만 뒀다(기간은 후속 — 반품은 건수가 적다).

- FE `/admin/returns`: 상태 칩 + 유형 select + 대행 전이 버튼(현재 상태에서 가능한 액션만). 대행은 주문 경로(`PATCH /api/orders/{orderId}/returns/{returnId}/status`)라 반품이 그 주문 소속인지 서버가 재검증한다. 어드민 NAV에 추가.

## 2026-08-07 — 🔁 교환 신청 UI + 📅 취소사유 집계 기간 필터 (백로그 🟡 잔여 2건 소진)

배포 전 남아 있던 backlog "자율 진행 중 발견 — FE·API 갭"의 마지막 두 건. 둘 다 **결정이 필요해 자율 진행이 손대지 않고 남겨둔** 항목이라, 오너 결정 3건을 먼저 받고 구현했다.

### 오너 결정 (AskUserQuestion 3문)
1. **교환 대체 옵션의 출처 = 기존 상품 상세 API 재사용** — 전용 엔드포인트를 새로 만들지 않는다. `GET /api/products/{id}`의 `options`가 이미 `available`(가용재고=stock−reserved)·`soldOut`을 담고 있고, 주문 항목 응답에 `productId`·`optionId`가 있어 FE만으로 화면이 성립한다.
2. **품절 옵션 = 신청 시점에도 가용재고 검증** — 예전엔 확정(검수 후 COMPLETE) 시점에만 재고를 봤다.
3. **취소사유 집계의 기간 축 = `order_item.cancelled_at` 신설(V54)** — 주문일 기준(코호트)이 아니라 "이탈이 발생한 시각".

### 1) 교환 신청 UI (구매자)

백엔드는 #3 P6에서 이미 교환(옵션 스왑)을 지원했는데 **FE에 신청 경로가 없어** 실질적으로 죽어 있던 기능이었다.

- **FE `/orders/[id]` 모달을 반품/교환 2탭으로**: 교환 탭을 처음 열 때만 `GET /api/products/{productId}`를 지연 조회(반품만 할 사람에게 불필요한 요청을 만들지 않는다) → 현재 사이즈를 제외한 옵션을 칩으로, 주문 수량보다 가용재고가 적으면 "품절"로 비활성. 사유 라벨도 교환 맥락으로 분기(`EXCHANGE_REASONS` — 같은 `CancelReason` enum에 라벨만 다르게).
- **모달 안에도 에러를 표시**: 서버 문구(기한 초과·중복 요청·품절)가 모달 뒤에서만 뜨던 것을 모달 내부에도 노출.
- **판매중지·삭제 상품**은 옵션 조회가 실패하므로 "교환 불가" 안내로 폴백하고 반품 탭은 그대로 쓸 수 있게 뒀다.

**BE — 신청 시점 검증(`ReturnService.create`)**: 예전에는 품절/다른 상품 옵션으로 신청해도 통과해 **승인→수거→검수까지 다 끝난 뒤에야 409/400**이 났다(구매자·셀러 양쪽의 헛수고). 신청 단계에서 같은 규칙을 먼저 본다.
- `requireExchangeOption`으로 **형태 검증(존재·같은 상품·현재와 다른 옵션)을 한 곳에 모아** 신청·확정이 같은 규칙을 쓰게 했다 — 둘이 갈리면 "신청은 되는데 확정은 안 되는" 요청이 생긴다.
- 재고는 신청=스냅샷(`available()`), 확정=원자적 소진으로 **게이트가 다르다**. 신청 검증은 예약이 아니므로 "신청 때는 있었는데 확정 때 품절"은 여전히 409로 막힌다 — 그 레이스를 테스트로 못 박았다(신청 시 재고 1 → 검수 사이에 0으로 → 확정 409·원 항목 미변경).

### 2) 취소·반품 사유 집계 기간 필터

지금까지 전체 기간 집계뿐이었다. 막혀 있던 이유는 **"언제 취소됐나"를 아무도 안 들고 있었기 때문**이다.
- `order_item.updated_at`은 교환 옵션 스왑·반품 flip 등 취소와 무관한 변경에도 갱신된다.
- `order_status_history`는 **주문 단위**라 항목 부분취소는 전이 자체가 없어 아예 안 잡힌다.

→ **V54 `order_item.cancelled_at`**(add-only·nullable) 신설. 모든 취소 경로가 `OrderItem.cancel()` 하나를 지나므로 기록 지점도 한 곳이다. 사유(`cancelReason`)와 달리 **시스템 취소(만료 등)에도 시각은 남긴다** — 사유는 몰라도 시각은 항상 알고, 그래야 기간 합계가 전체 건수와 어긋나지 않는다. 기존 취소 항목은 마이그레이션에서 `updated_at`으로 1회 근사 백필.

반품 쪽은 `return_request.created_at`(요청 시각)이 이미 명확해 컬럼 추가가 필요 없다 → **두 축이 모두 "이탈이 발생한 시각"으로 통일**된다.

- `GET /api/dashboard/cancel-reasons?from=&to=`(각각 선택·`yyyy-MM-dd`). 필터는 대사 윈도우와 같은 **nullable 바인딩**(null이면 그 경계 무시), 상한은 배타(`to+1일 00:00`)로 잡아 **to 당일을 포함**한다. 종료일이 시작일보다 빠르면 빈 결과로 조용히 넘기지 않고 400.
- FE 어드민 위젯에 기간 칩(전체/7일/30일/90일). **기간을 걸어 0건이 되어도 위젯을 숨기지 않는다** — 숨기면 칩이 사라져 되돌릴 수 없다. `toISOString`은 UTC로 밀려 한국 시간대에서 하루가 어긋나므로 로컬 날짜를 직접 조립.

### 테스트 조정 (의도한 개선의 부작용)
신청 시점 검증이 생기면서 **기존 테스트 3건이 더 이른 지점에서 실패**하게 됐다 — 그게 목적이라 기대치를 앞당겼다.

### 급소 — "그냥 덜 환불"이 왜 틀렸나

취소 환불 공식은 한 줄이다: `refundNow = (결제액 − 환불누계) − payable`.
이건 **`결제액 − 환불누계 == payable`** 항등식을 전제한다. 회수비 3000원을 payable 손대지 않고 덜 환불하면
잔여가 payable보다 3000 크게 남고, **같은 주문의 다른 항목을 취소하는 순간 그 3000이 자동 환불**된다.
고객이 회수비를 되돌려받는 무음 누수이고, **단건 반품만 보면 정상으로 보이기 때문에** 더 위험하다.

해법은 #4가 배송비에 쓴 것과 **같은 트릭** — 차감액을 `payable`에 되싣는 것(`orders.return_shipping_charge`).
기존 공식을 한 글자도 고치지 않고 회수비가 보존된다. 회귀 테스트(`ReturnShippingChargeTest ★`)는
셀러1 배송완료(반품 가능)+셀러2 미출고(취소 가능)인 멀티셀러 주문에서 A 반품 후 B 취소 시
환불 누계가 30000이 아니라 **27000**임을 못 박는다.

클램프도 필수다: `charge = min(스냅샷 요율, 실효가)`. 없으면 저가·고할인 라인에서 음수 환불이 되어
`refundForReturn`의 `<=0` 조기 리턴에 걸리거나(무음 손실) `Payment`가 400을 던져 반품 트랜잭션 전체
(flip·재입고·쿠폰 복원)가 롤백된다.

### 왜 귀책을 스냅샷하는가

`fault`는 `CancelReason` enum 생성자에서 **읽기 시점에 파생**되는 값이었다. 이걸 그대로 돈에 쓰면
매핑을 한 줄만 바꿔도(예: `DELIVERY_DELAY`를 SELLER→PLATFORM) **이미 환불·정산·지급이 끝난 과거 건의
귀책까지 소급 재분류**되어 감사 추적이 무너진다. → 돈이 확정되기 직전(검수)에 `return_request.fault_party`로
스냅샷하고 이후 계산은 이 컬럼만 읽는다. `discount_funded_by`가 이미 만들어 둔 선례와 같은 패턴이다.

그리고 **구매자 자기신고를 그대로 돈에 연결하면 안 된다** — FE 반품 모달은 `DEFECTIVE`·`WRONG_DELIVERY`
(둘 다 SELLER 귀책)를 구매자 선택지로 노출한다. 지금 상태로 부과하면 전원이 '상품 불량'을 눌러 회수비를
회피한다. 반대로 셀러 확정만 두면 셀러가 자기 이익 방향으로 판정한다 → **3단 방어**(판정·재정을 이력에 기록 /
ADMIN이 종료 전까지 `SET_FAULT`로 재정 / 재정을 액션보다 **먼저** 반영해 같은 요청에 REFUND가 실려 와도
새 귀책으로 계산)로 닫았다.

### ★ 정산 게이팅 3곳 — 기존 테스트가 절대 못 잡는 자리

기존 정산 테스트는 전부 "정방향 정산이 이미 있는" 상태만 다룬다. 회수비 엔트리가 **정방향보다 먼저**
생기는 순서(반품이 먼저 확정된 결제)를 아무도 검증하지 않는데, 그 순서에서만 다음이 터진다.

1. **`run()`의 멱등 게이트가 결제 단위**면 → 그 결제는 영원히 정방향 미정산 = **셀러 매출 전액 소실**
   → `existsByPaymentIdAndEntryKindIn(SALE, SHIPPING)`으로 종류를 좁혔다.
2. **역분개 진입 게이트가 `existing.isEmpty()`**면 → 셀러 `target − 0`의 **양수** diff가 생겨
   역분개가 정방향 정산을 재생성 = **이중 지급** → 매출 원장 엔트리 존재 여부로 판정.
3. **셀러 루프가 SALE 외를 포함**하면 → 플랫폼 엔트리가 `null` 버킷에 섞여 매 실행 역분개되고,
   `platformRateBySeller.putIfAbsent`가 새 kind의 요율 `0.0`을 먼저 집어 `dPlatformFee`가 0이 되는
   **리스트 순서 의존 버그**까지 겹친다 → SALE만 집계하고 나머지는 각자 target과 비교.

셋 다 회귀 테스트로 고정했다(`SettlementReturnShippingTest ★` 3건).

### 왜 boolean을 늘리지 않고 enum인가

엔트리 종류 축은 `reverseRefunds`의 **버킷 분기**에 직접 쓰인다. 역분개는 "지금의 target − 이미 정산된 합"만
남기므로, **어느 버킷에도 속하지 않은 엔트리는 매 실행마다 통째로 역분개돼 조용히 사라진다**(#4가 배송비에서
실제로 밟았던 함정). boolean 3개면 유효 조합 4가지를 8가지로 표현할 수 있어 "빠진 버킷"이 타입으로 막히지
않는다. enum이면 **"모든 엔트리는 정확히 하나의 kind, 모든 kind는 자기 target"**이 구조로 강제된다.

### 두 성격의 돈을 같은 컬럼에 뭉치면 대사가 갈린다

- **회수비(RETURN_SHIPPING)** = 고객에게서 덜 환불해 플랫폼이 실제로 보유 → **PG 잔여에 실재하는 돈**
  → `gross`에 실어 Σgross(원장 총액)를 복원.
- **귀책 과금(FAULT_CHARGE)** = 셀러↔플랫폼 **내부 정산 조정액** → PG 원장에 대응 금액이 **없다**
  → `gross=0`·`charge_amount`에만 실어 net만 줄인다. gross에 실으면 대사가 즉시 AMOUNT_MISMATCH로 튄다.

## 2026-08-12 — 💸 #8 후속 P6: 음수 정산 이월 잔액 모델

위 P4가 남긴 **알려진 한계**를 스모크에서 실물로 만났다 — 셀러15의 미지급 잔액이 −113,128원이라
지급 시도가 `정산 순액이 음수입니다`로 **전액 거부**됐다. 정상 매출까지 통째로 막히고, 셀러 체감은
"정산이 안 나왔다"다. 게다가 음수 항목이 `payout_id=null`로 남아 "다음에 더 넓은 기간으로 쓸어담기"를
기대하는 구조라 **얼마나 넓혀야 하는지 아무도 알 수 없었다**.

**오너 결정 = 이월 잔액 모델**(BE + 정산서 화면).

```
settleable   = 이번 기간 net + carried_in(≤0)
total_net    = max(0, settleable)   ← 음수 송금은 여전히 만들지 않는다
carried_over = min(0, settleable)   ← 부족분만 다음으로
```

핵심은 **지급액이 0이어도 묶음을 만들고 기간 항목을 전부 편입**하는 것이다. 항목이 정확히 한 번만
소비되고, "이 기간은 0원 정산, N원 이월"이라는 기록이 남아 **지급 이력이 끊기지 않는다**.
파생 계산은 `Payout` 생성자가 한다(`netAmount`가 이미 파생값인 것과 같은 방식).

`carried_in`은 **그 셀러의 가장 최근 payout(id desc)**에서 이어받는다. 기간(periodTo)이 아니라 id 기준인
이유는, 과거 기간을 뒤늦게 정산하는 경우 기간 기준으로 고르면 **같은 이월을 두 번 태울** 수 있기 때문이다.

🟢 **런타임 실증**: 아까 막혀 있던 셀러15로 다시 지급 → payout #4 = 지급 **0원** · 차월 이월 **−113,128** ·
항목 1건 편입 · 셀러15 미지급 잔여 **0건**. FE는 어드민 지급 목록에 "이월" 열, 셀러 정산서에
"전월 이월 N 차감 / 차월 이월 N"을 노출한다 — 셀러가 **왜 덜 받았는지** 볼 수 있어야 이 모델이 의미가 있다.
