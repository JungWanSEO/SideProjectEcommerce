## 2026-07-01 (이어서) — 카카오 소셜 로그인 (OAuth2, email-free)

구글에 이어 카카오 추가. 착수 전 deep-research로 2026.6 재검증(카카오 로그인 무료·닉네임/프로필 무검수·email은 비즈앱+검수). 사용자가 Kakao Developers에서 REST API키·Client Secret 발급, 나는 구현.

### 🐛 실 버그 2건 발견·수정 (런타임 검증의 값어치)
- **① provider별 opt-in 부팅 실패**: `spring.security.oauth2.client.*`에 카카오를 빈 값으로 두니 Boot가 **모든 registration을 검증** → 구글만 채우고 카카오 비우면 *"Client id of registration 'kakao' must not be empty"* 로 **부팅 실패**. → `spring.security.oauth2.client.*` 폐기, 자격증명을 `app.oauth2.*`로 받아 **client-id 채워진 provider만** 골라 `ClientRegistrationRepository`를 직접 만드는 `OAuth2ClientConfig`로 교체(진짜 provider별 opt-in·배포 시 한쪽만 켜도 안전). 부팅 로그로 발견.
- **② 카카오 id 캐스팅**: `String.valueOf(principal.getAttribute("id"))` — `getAttribute`가 제네릭 `<A>A`라 컴파일러가 `String.valueOf(char[])` 오버로드를 골라 **런타임 ClassCastException(Long→char[])**. Whitelabel /error로 표출. → `principal.getName()`(user-name-attribute "id" 값 문자열) 사용. **회귀 테스트 추가**(`OAuth2LoginSuccessHandlerTest` — Long id 재현).

### 구현
- 카카오는 Spring 내장 provider가 아니라 `OAuth2ClientConfig`에서 엔드포인트 직접 지정(`kauth.kakao.com`·`kapi.kakao.com/v2/user/me`·userNameAttribute `id`·scope `profile_nickname,profile_image`·secret 있으면 `client_secret_post`).
- 성공 핸들러 **provider별 파싱**: 구글=sub/email/name(평면), 카카오=`id`(getName)·`kakao_account.profile.nickname`·email(있으면). email 없으면 `MemberService`가 **플레이스홀더 email**(`kakao_<id>@social.local`)로 생성(NOT NULL·UNIQUE 충족·스키마 무변경). find-or-create + `AuthService.issueTokens` 재사용은 구글과 동일.
- FE: `GoogleLoginButton`→`SocialLoginButtons`(구글+카카오)로 확장.

## 2026-07-14 (이어서 4) — @RateLimit AOP 일반화 + 429 Retry-After

### 맥락
- 백로그 READY 5번(자율진행). `rateLimiter.check("login:" + email, 5)`처럼 **키를 손으로 조립**하는 코드가 3곳(로그인·쿠폰 claim·상품 피드)에 흩어져 있었다. 문제는 셋: ①키 규칙이 분산 ②제한을 걸려면 업무 코드를 고쳐야 함 ③IP 기준을 쓰려고 **컨트롤러가 `HttpServletRequest`까지 주입**받음.

### 추가
- **`@RateLimit(key, limit, by)` + `RateLimitAspect`** — `@Auditable`과 같은 결(횡단 관심사는 AOP로).
  - `by`(SpEL)로 인자에서 식별자: `#request.email()`(로그인)·`#memberId`(claim). 비우면 **클라이언트 IP**(공개 피드).
  - 요청 컨텍스트가 없으면(스케줄러·배치) `unknown`으로 센다 — 키가 통째로 사라져 **제한이 조용히 무력화되는 것**을 막는다.
- **429에 `Retry-After` 헤더**(RFC 9110) — `RateLimitExceededException`(retryAfterSeconds=60, 윈도우 1분)을 리미터 3종이 던지고, GlobalExceptionHandler의 **더 구체적인 핸들러**가 헤더를 붙인다. 헤더가 없으면 클라이언트는 언제 다시 와야 할지 몰라 **즉시 재시도(부하 증폭)** 하거나 과하게 오래 기다린다.
- 세 호출부 전환 + `ProductController`에서 `HttpServletRequest`·`clientIp()` 제거(컨트롤러가 다시 얇아짐).
